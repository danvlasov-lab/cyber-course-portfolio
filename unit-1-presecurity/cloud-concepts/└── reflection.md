## 1. Cloud in your own words
Instead of buying physical hardware and storing it in your own building, you are renting access to computing power, storage space, and software owned by big tech companies like Microsoft or Amazon over the internet. When you buy a personal computer, you own the machine, but you are also entirely responsible for updating it, fixing hardware failures, and buying a new one when it gets outdated. Renting internet-based computing power flips this model into a utility like electricity, allowing you to instantly scale resources up or down on demand without worrying about physical repairs or upfront hardware purchases.

## 2. Traditional → Cloud → Containers
The underlying pattern across all four stages is a continuous effort to maximize hardware efficiency, speed up software deployment, and abstract away unnecessary layers of management. Traditional IT bound software directly to physical servers, which wasted resources and took weeks to provision. Virtualization solved hardware waste by running multiple virtual machines on a single physical server, while remote hosting platforms solved deployment speed by letting users spawn those machines instantly over the internet. Containers took this evolution a step further by removing the need for a full operating system for every application, allowing code to run in lightweight, consistent environments that launch in seconds.
   
## 3. Deployment vs Service models
Deployment models answer where the computing infrastructure physically lives and who has access to it, whereas service models answer what level of control and management you are taking on versus what the vendor handles. Public deployment means infrastructure is shared over the internet, while SaaS provides a fully managed, ready-to-use software application. A concrete example of a service combining both is Microsoft 365 (or Gmail), which runs in a public infrastructure environment accessible over the internet while providing complete, managed software directly to the end user without requiring them to maintain code or servers.

## 4. The Shared Responsibility Model
The Shared Responsibility Model states that while cloud vendors secure the underlying physical infrastructure, hardware, and core platform code, customers remain responsible for securing everything they put into that environment. Moving to remote infrastructure does not transfer security obligations because vendors cannot control your data, user access permissions, or how you configure your software. Regardless of whether you use IaaS, PaaS, or SaaS, you are always responsible for managing data classification, user identity permissions, and device access rules. A famous real-world example of customer failure is the 2019 Capital One data breach, where a misconfigured web application firewall and over-privileged access roles allowed an attacker to access sensitive customer records stored in AWS S3 buckets—an issue entirely caused by customer misconfiguration rather than a flaw in Amazon's physical hardware.  

## 5. Why organisations still hesitate
One major reason organizations resist a complete move to remote platforms is regulatory and data residency compliance, such as the EU’s GDPR framework. Many government entities, healthcare providers, or financial institutions are legally mandated to keep sensitive citizen data within specific physical national boundaries or under strict localized custody, which can be difficult to guarantee in global public infrastructure setups. A second distinct reason is vendor lock-in and long-term cost unpredictability. Organizations fear becoming heavily dependent on proprietary vendor tools—making future migrations prohibitively expensive—while struggling to predict monthly operational costs when dynamic workload scaling unexpectedly spikes billing.

## 7. Cloud in an entry-level tech role
As an entry-level helpdesk or sysadmin technician, you will frequently handle identity management and access issues that stem directly from cloud identity providers like Entra ID (formerly Azure AD). For example, a technician might receive a ticket from a remote user locked out of their workstation because a conditional access policy triggered an alert on a suspicious cloud sign-in attempt, requiring the technician to reset their multi-factor authentication (MFA). Another common scenario involves troubleshooting software access, such as investigating why a corporate user cannot sync local files to Microsoft OneDrive due to improper licensing assignments or revoked active directory permissions within the admin tenant.

## 7. Your personal takeaway
The biggest shift in my perspective is realizing that offloading infrastructure to external vendors is not a magical security shortcut, but rather a shift in where technical responsibility lives. I used to assume that moving data away from local hard drives meant security was fully handled by companies with multi-billion-dollar security budgets. Understanding the shared responsibility boundary makes me realize that human misconfigurations and weak access controls are still the main attack vectors, which makes mastering identity management and configuration security far more practical for my future tech career than just knowing how physical servers operate.
